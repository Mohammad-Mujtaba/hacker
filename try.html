Jinja2 Basics

Jinja2 is a modern and designer-friendly templating language for Python, modeled after Django's templates. It's fast, widely used, and secure with sandboxed template execution.

Why Jinja2 for Network Automation?

  • Generate consistent network device configurations
  • Create dynamic templates for multiple devices
  • Reduce human error in repetitive configurations
  • Integrate with tools like Ansible, SaltStack, and FortiManager

Template Syntax Basics

Jinja2 uses specific delimiters for different purposes:

Syntax Purpose Example
{{ ... }} Output/print a variable or expression {{ hostname }}
{% ... %} Control structures (if, for, etc.) {% for interface in interfaces %}
{# ... #} Comments (not included in output) {# This is a comment #}
## ... ## Line statements (if configured) ## for item in list
Basic Template Example
hostname {{ device.hostname }} ! {# Interface configuration #} {% for interface in device.interfaces %} interface {{ interface.name }} description {{ interface.description }} ip address {{ interface.ip }} {{ interface.netmask }} {% if interface.vlan %} vlan {{ interface.vlan }} {% endif %} ! {% endfor %}

Note: Jinja2 templates are just text files with special syntax. They don't execute code directly but generate text output based on the template and provided data.

Working with Variables

Variables are named containers that store data values. They allow you to insert dynamic content into your templates and make them reusable across different contexts.

What Are Variables in Jinja2?

In Jinja2, variables are placeholders that get replaced with actual values when the template is rendered. They:

  • Act as references to data passed to the template
  • Can represent simple values or complex objects
  • Make templates dynamic and reusable
  • Are case-sensitive (myVar is different from myvar)

Variable Data Types

Jinja2 supports several data types that variables can hold:

Data Type Description Example
String Text data (enclosed in quotes) {{ "Firewall Policy" }}
Number Integer or floating-point numbers {{ 42 }} or {{ 3.14 }}
Boolean True/False values {{ true }} or {{ false }}
List/Array Ordered sequence of items {{ [1, 2, 3] }}
Dictionary/Object Key-value pairs {{ {'name': 'FW1', 'ip': '192.168.1.1'} }}
None Represents no value {{ none }}

Note: In FortiManager templates, you'll often work with strings (for names, descriptions), numbers (for IDs, ports), and dictionaries (for complex objects like policies).

Accessing Variables

Variables are accessed using the {{ variable_name }} syntax:

System hostname: {{ hostname }} Current date: {{ current_date }} Policy status: {{ policy.active }}

Variable Attributes

Access attributes of objects using dot notation:

Interface IP: {{ interface.ip_address }} Subnet Mask: {{ interface.subnet_mask }} VLAN ID: {{ interface.vlan.id }}

Dictionary Access

Access dictionary items with dot notation or subscript syntax:

Device model: {{ device.model }} {# dot notation #} Device model: {{ device['model'] }} {# subscript syntax #} Device location: {{ device.get('location', 'Unknown') }} {# with default #}
FortiManager Variable Example with Data Types
config firewall policy edit {{ policy.id }} {# Number #} set name "{{ policy.name }}" {# String #} set srcintf "{{ policy.source_interface }}" set dstintf "{{ policy.destination_interface }}" set srcaddr {{ policy.source_addresses|join(' ') }} {# List #} set dstaddr {{ policy.destination_addresses|join(' ') }} set action {{ policy.action|lower }} {# String converted to lowercase #} set schedule "{{ policy.schedule }}" set service "{{ policy.service }}" set logtraffic {{ policy.log_traffic|default('enable') }} {# Boolean-like string #} {% if policy.tags %} {# List check #} set tags {{ policy.tags|join(' ') }} {% endif %} next end

Default Values

Use the default filter to provide fallback values when a variable might be undefined:

Logging: {{ logging_enabled|default('disabled') }} {# String default #} Port: {{ port_number|default(80) }} {# Number default #} Retry count: {{ retries|default(3) }}

Warning: If a variable doesn't exist and you don't use a default, Jinja2 will raise an undefined error unless you've configured it to ignore such cases. Always provide defaults for optional fields in production templates.

Checking Variable Types

You can check variable types using the is operator with these tests:

{% if policy.action is string %} {# Action is a string #} {% endif %} {% if port_number is number %} {# Port is a number #} {% endif %} {% if address_list is iterable %} {# Can loop through address_list #} {% endif %} {% if setting_value is none %} {# Value is not provided #} {% endif %}

Control Structures and Logic

Jinja2 provides several control structures to add logic to your templates.

If Statements

Conditionally include content based on conditions:

{% if device.type == 'firewall' %} set security-level high {% elif device.type == 'switch' %} set security-level medium {% else %} set security-level low {% endif %}

Comparison Operators

Jinja2 supports standard comparison operators:

Operator Description Example
== Equal to {% if vlan == 10 %}
!= Not equal to {% if status != 'down' %}
> Greater than {% if count > 5 %}
>= Greater than or equal {% if version >= 6.4 %}
< Less than {% if latency < 100 %}
<= Less than or equal {% if errors <= 0 %}
and Logical AND {% if active and not disabled %}
or Logical OR {% if http or https %}
not Logical NOT {% if not maintenance_mode %}
FortiGate Policy Example
config firewall policy edit 0 set srcintf "port1" set dstintf "port2" set srcaddr "all" set dstaddr "all" set action accept {% if policy.requires_authentication %} set identity-based enable set identity-based-policy {{ policy.auth_policy_id }} {% endif %} {% if policy.logs_traffic %} set logtraffic all {% else %} set logtraffic disable {% endif %} set schedule "always" set service "ALL" next end

Tests

Jinja2 provides tests that can be used with the is operator:

{% if interface.status is defined %} {# Interface status exists #} {% endif %} {% if ip_address is not none %} {# IP address is not null #} {% endif %}

Common tests:

  • defined - check if variable exists
  • none - check if value is None
  • even - check if number is even
  • odd - check if number is odd
  • lower - check if string is lowercase
  • upper - check if string is uppercase

Loops and Iteration

Jinja2 provides powerful looping constructs to handle repetitive tasks.

For Loops

Iterate over sequences (lists, tuples) and dictionaries:

{% for interface in interfaces %} interface {{ interface.name }} description {{ interface.description }} ip address {{ interface.ip }} {{ interface.netmask }} ! {% endfor %}

Loop Variables

Inside a loop, you have access to special variables:

Variable Description
loop.index Current iteration (1-based)
loop.index0 Current iteration (0-based)
loop.revindex Iteration from end (1-based)
loop.revindex0 Iteration from end (0-based)
loop.first True if first iteration
loop.last True if last iteration
loop.length Total number of items
Loop Variables Example
{% for user in users %} User #{{ loop.index }}: {{ user.name }} {% if not loop.last %}, {% endif %} {% endfor %}

Dictionary Iteration

Iterate over dictionary keys and values:

{% for key, value in settings.items() %} set {{ key }} "{{ value }}" {% endfor %}
FortiManager Address Group Example
config firewall addrgrp edit "{{ group.name }}" set member {% for address in group.members %}"{{ address }}"{% if not loop.last %} {% endif %}{% endfor %} set comment "{{ group.description }}" next end

Loop Controls

Control loop execution with these statements:

{% for item in list %} {% if item == 'skip' %} {% continue %} {# Skip to next iteration #} {% endif %} {{ item }} {% if item == 'break' %} {% break %} {# Exit loop entirely #} {% endif %} {% endfor %}

Filters

Filters transform variable output. They are applied with the pipe (|) symbol.

Common Built-in Filters

Filter Description Example
default Provide default if value is undefined {{ log_level|default('info') }}
length Get length of sequence {{ interfaces|length }}
lower Convert to lowercase {{ hostname|lower }}
upper Convert to uppercase {{ protocol|upper }}
trim Strip whitespace {{ description|trim }}
replace Replace substrings {{ path|replace(' ', '_') }}
join Join sequence with string {{ vlans|join(',') }}
batch Batch items into lists {{ ips|batch(3) }}
tojson Convert to JSON {{ config|tojson }}
ipaddr IP address manipulation (if available) {{ '192.168.1.1'|ipaddr('netmask') }}
Filter Examples
{# Ensure interface name is lowercase with no spaces #} interface {{ interface.name|lower|replace(' ', '_') }} {# Join multiple VLANs with commas #} switchport trunk allowed vlan {{ vlan_list|join(',') }} {# Default value for optional setting #} set logging {{ logging_level|default('disable') }}

Chaining Filters

Filters can be chained together:

{{ description|trim|lower|replace(' ', '-') }}

Custom Filters

In Python environments, you can create custom filters. For FortiManager, you might have filters like:

{# Hypothetical custom filter #} set policy-id {{ policy.name|fortigate_safe_name }}

Note: The availability of custom filters depends on your Jinja2 environment. In FortiManager, you may have access to specific Fortinet-related filters.

Macros and Reusable Components

Macros are like functions in Jinja2 - reusable template components.

Basic Macro

Define and call macros to avoid repetition:

{% macro interface_config(name, ip, netmask, description='') %} interface {{ name }} description {{ description|default('') }} ip address {{ ip }} {{ netmask }} ! {% endmacro %} {# Use the macro #} {{ interface_config('GigabitEthernet0/1', '192.168.1.1', '255.255.255.0', 'Management interface') }} {{ interface_config('GigabitEthernet0/2', '10.0.0.1', '255.255.255.0') }}

Macro Arguments

Macros can have required and optional arguments:

{% macro fortigate_policy(id, srcintf, dstintf, srcaddr, dstaddr, action='accept', log='enable') %} config firewall policy edit {{ id }} set srcintf "{{ srcintf }}" set dstintf "{{ dstintf }}" set srcaddr "{{ srcaddr }}" set dstaddr "{{ dstaddr }}" set action {{ action }} set logtraffic {{ log }} next end {% endmacro %} {# Using the macro #} {{ fortigate_policy(1, 'port1', 'port2', 'all', 'all') }} {{ fortigate_policy(2, 'port1', 'port3', 'internal_net', 'webservers', action='deny', log='disable') }}

Importing Macros

Store macros in separate files and import them:

{% from 'fortigate_macros.j2' import fortigate_policy %} {{ fortigate_policy(1, 'port1', 'port2', 'all', 'all') }}
FortiManager Macro Library Example
{# fortinet_macros.j2 #} {% macro fortigate_address(name, ip, associated_interface='') %} config firewall address edit "{{ name }}" set associated-interface "{{ associated_interface }}" set subnet {{ ip }} next end {% endmacro %} {% macro fortigate_service(name, protocol, port) %} config firewall service custom edit "{{ name }}" set {{ protocol }} {{ port }} next end {% endmacro %}

Pro Tip: Create a library of macros for common FortiManager configuration patterns to dramatically speed up your template development.

FortiManager Specific Jinja2 Usage

Special considerations and patterns for FortiManager automation.

FortiManager Template Structure

Typical structure for device or policy templates:

## FMG-Dynamic-Mapping ## ==== Device Level ==== config system global set hostname {{ hostname|default('FortiGate') }} set timezone {{ timezone|default('04') }} end ## ==== Policy Package ==== config firewall policy {% for policy in policies %} edit {{ policy.id }} set name "{{ policy.name }}" set srcintf "{{ policy.srcintf }}" set dstintf "{{ policy.dstintf }}" set srcaddr "{{ policy.srcaddr }}" set dstaddr "{{ policy.dstaddr }}" set action {{ policy.action|default('accept') }} set schedule "{{ policy.schedule|default('always') }}" set service "{{ policy.service|default('ALL') }}" {% if policy.nat %} set nat {{ policy.nat|lower }} {% endif %} next {% endfor %} end

Dynamic Variables in FortiManager

FortiManager provides special variables:

Variable Description
${name} Device name
${serial} Device serial number
${ip} Device IP
${dynamic} Dynamic mapping values
Dynamic Interface Assignment
config system interface edit "port1" set mode static set ip ${dynamic.port1.ip}/${dynamic.port1.netmask} set allowaccess {{ mgmt_allow_access|default('ping https ssh') }} set description "MGMT - ${name}" next end

Best Practices for FortiManager Templates

  • Use consistent naming conventions for variables
  • Include comments explaining complex sections
  • Provide default values for optional settings
  • Group related configurations together
  • Use macros for frequently repeated configurations
  • Test templates with various input data
Complete FortiGate Template Example
## FMG-Device-Template ## Basic System Configuration config system global set hostname ${name} set admintimeout {{ admin_timeout|default('480') }} set timezone {{ timezone|default('04') }} end config system interface {% for interface in interfaces %} edit "{{ interface.name }}" set vdom "root" set ip {{ interface.ip }}/{{ interface.netmask }} set description "{{ interface.description }}" {% if interface.allowaccess %} set allowaccess {{ interface.allowaccess }} {% endif %} set status up next {% endfor %} end ## Firewall Address Objects config firewall address {% for address in firewall_addresses %} edit "{{ address.name }}" set subnet {{ address.ip }}/{{ address.netmask }} {% if address.associated_interface %} set associated-interface "{{ address.associated_interface }}" {% endif %} next {% endfor %} end ## Firewall Policies config firewall policy {% for policy in firewall_policies %} edit {{ policy.id }} set name "{{ policy.name }}" set srcintf "{{ policy.srcintf }}" set dstintf "{{ policy.dstintf }}" set srcaddr "{{ policy.srcaddr }}" set dstaddr "{{ policy.dstaddr }}" set action {{ policy.action }} set schedule "{{ policy.schedule|default('always') }}" set service "{{ policy.service|default('ALL') }}" set logtraffic {{ policy.logtraffic|default('enable') }} next {% endfor %} end

Troubleshooting FortiManager Templates

Common issues and solutions:

Issue Solution
Variables not expanding Check variable names match input data, ensure proper delimiters ({{ }})
Syntax errors Validate template with a Jinja2 validator before importing
Unexpected whitespace Use whitespace control ({%- and -%})
Dynamic mappings not working Verify dynamic variable names match database fields
Missing defaults Always provide default values for optional settings

Troubleshooting and Best Practices

Common Jinja2 Errors

Error Cause Solution
UndefinedError Variable not defined Use default filter or ensure variable exists
TemplateSyntaxError Invalid syntax Check for missing %} or other syntax issues
Unexpected whitespace Control structures add newlines Use whitespace control ({%- and -%})
Filter not found Filter not available Check filter name or create custom filter

Whitespace Control

Control whitespace in output with - in tags:

{% for item in list -%} {{ item }} {%- endfor %}

The - removes whitespace before or after the tag.

Debugging Techniques

  • Use {{ variable|tojson }} to inspect complex variables
  • Add debug comments with {# DEBUG: ... #}
  • Break complex templates into smaller parts
  • Test with simplified data first
  • Use online Jinja2 testers for validation
Debugging Example
{# DEBUG: Show all available variables #} {# {{ vars()|tojson }} #} {# DEBUG: Check interface data structure #} {# {{ interfaces|tojson }} #} {% for interface in interfaces %} interface {{ interface.name }} {# DEBUG: Show full interface object #} {# {{ interface|tojson }} #} ip address {{ interface.ip }} {{ interface.netmask }} ! {% endfor %}

Best Practices

  • Keep templates readable - add comments and spacing
  • Use consistent naming conventions
  • Provide defaults for optional values
  • Validate input data before templating
  • Create reusable macros for common patterns
  • Document template requirements
  • Test with edge cases (empty lists, missing values)
